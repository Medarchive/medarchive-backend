OPEN QUESTIONS FOR PRODUCT
======================================================================

1. DECIDED + BUILT. Clinical proofs are authenticated-only, reusing the
   existing access-control model — not exposed via the public Care ID
   share link (that link stays identity-only: careId/status/wallet/name).
   "Care ID integration" means the patient's own dashboard: GET /dashboard
   now includes the 5 most recent clinical proofs (id, type, claim,
   status, timestamps — no cryptographic material), cache-invalidated on
   proof create and on generation complete/fail.

2. DECIDED + BUILT (2026-09-24). Two deliberate routes, both real:
   - Email+password signup (POST /auth/register): still auto-provisions a
     custodial wallet, same as before — but now via a background BullMQ
     job (WALLET_PROVISION_QUEUE / WalletProvisionProcessor), not inline
     in the registration transaction. Registration no longer waits on
     keypair generation or the testnet funding call. The wallet is
     verifiedAt-stamped immediately on creation (server holds the key —
     no SEP-53 challenge is meaningful for a wallet the user never held).
   - Wallet-first / non-custodial (POST /auth/wallet-nonce + POST
     /auth/use-wallet for login; POST /wallet + POST /wallet/verify to
     link): already existed, untouched, server never sees a secret.
   - New: POST /wallet/create lets anyone without a wallet provision a
     custodial one on demand post-signup (e.g. if the background job
     failed, or for a user created outside register(), like
     activateProvider()'s invitation flow, which never auto-provisioned
     one). Same underlying WalletService.create() the background job calls.
   Non-custodial payment/proof flows are unaffected either way — none of
   ServiceOrdersService/StellarService's checks depend on encryptedSecret.
   ZK-record anchoring (anchorFromUserWallet) still silently no-ops for a
   secret-less wallet — unchanged, not a new gap.
