BASELINE — what already exists (v1, confirmed in repo)
======================================================================
- Care ID: generate/get, 24h shareable public link (src/care-id/*)
- Health records CRUD with types: BLOOD_TEST, PRESCRIPTION, SCAN, LAB_TEST,
  MEDICATION, REPORT, ALLERGY, OTHER (src/db/schema/health-records.ts)
- Generic ZK proof per health record: Poseidon commitment over
  (userId, recordType, fileS3Keys) — proves record integrity/existence,
  NOT a specific clinical predicate (src/zk-proof/*, src/db/schema/zk-proofs.ts)
- Provider-access flow: request record access -> patient approve/decline/revoke
  -> provider views approved record (src/provider-profile/*, provider-record-requests table)
- Wallet linking: add Stellar address, SEP-53 signature verification (nonce
  sign/verify), balance + transaction history via Horizon (src/wallet/*)
- CORRECTION (was understated originally): every user — patient or provider —
  gets a server-generated Stellar keypair at registration (auth.service.ts,
  register()), with the secret AES-256-GCM encrypted and stored in
  wallets.encryptedSecret. This system is custodial by default for
  essentially every wallet in it, not just an edge case used for ZK
  anchoring. See Open Question 2 (updated) below.
- Stellar service: XLM-only payment operation, used only to anchor/verify
  ZK proof commitments (0.0000001 XLM self-payment + memo hash).
- No payment, order, service, invoice, or USDC concept anywhere in repo
  at the time this doc was first written.

PART 1 — Expanded ZK Clinical Disclosures            STATUS: NOT STARTED
======================================================================

[ ] Define the additional clinical proof types (brief explicitly says this
    must happen "before implementation" — currently undefined). Existing
    three reference types (diagnosis category, allergy confirmation, prior
    prescription patterns) are NOT implemented as distinct predicates today
    — only a generic per-record existence proof exists. Action needed:
    - Decide + document the new proof-type list (beyond the 3 baseline ones)
    - For each type, define the exact predicate/claim being proven and its
      public inputs (e.g. "has an ALLERGY record where cause = X" without
      revealing other allergy fields)

[ ] Add a proof "type" dimension to the data model. Today healthRecordProofs
    is 1:1 with healthRecords and has no notion of "which fact is being
    proven" — it's a blanket integrity commitment. Needs:
    - New table/enum for clinical disclosure proof types
    - Link proof type -> which underlying record(s)/fields feed the circuit
    - Support multiple proofs of different types per record (current unique
      constraint on healthRecordId blocks more than one proof per record)

[ ] Build real predicate-based ZK circuits/logic per proof type (current
    zk-proof.processor.ts just hashes (userId, recordType, fileS3Keys) —
    this proves "a record was submitted," not a clinical fact). Needs
    per-type circuit/logic so the proof confirms the specific fact without
    exposing unrelated fields of the record.

[ ] Patient-facing "generate proof" flow: select a supported clinical fact
    type (not just "generate proof for this record"), confirm what will be
    proven/hidden, trigger generation, and background job handles the ZK
    work (queue infra already exists — reusable, but request shape needs a
    proofType, not just recordId).

[ ] Proof generation status UI/API per proof type: pending/generated/failed
    states already exist as enum — reusable, but response needs to carry
    proof type + human-readable description of what was proven.

PART 6 — Non-Custodial Wallet Connection (payments)   STATUS: MOSTLY DONE
======================================================================

[x] Payment flow does NOT use server-side signing. DEVIATION FROM ORIGINAL
    PLAN: instead of the server building an unsigned XDR for the client to
    sign, GET /service-orders/:id/payment-intent returns the raw payment
    parameters (destination, assetCode, assetIssuer, amount, memo). The
    patient's own wallet builds, signs, and submits the transaction
    entirely client-side — Med Archive never touches a signing key for
    this flow. Simpler than XDR relay and avoids server-side sequence-number
    races. verify-payment then checks the resulting tx hash against these
    same parameters.

[x] getPaymentIntent() and create() both now check hasUsdcTrustline() before
    proceeding — see trustline fix below.

[ ] Open Question 2 is now MORE concretely a problem, not resolved: every
    wallet in the system (patient or provider) is custodial by default
    (server holds an encrypted secret from signup). The payment flow itself
    is now non-custodial, but the underlying wallet model still isn't —
    product needs to decide whether that's acceptable for the hackathon
    scope or needs to change.

PART 8 — Payment Verification                          STATUS: DONE
======================================================================

[x] StellarService.verifyPayment(txHash, expected): fetches the tx from
    Horizon, checks successful=true, memo matches order.reference, finds a
    payment operation, checks destination/asset/amount all match. Returns
    {valid, reason}.

[x] Order flips to PAID only on a fully-matched, successfully-verified
    transaction (atomic DB update guarded by status=PENDING, so a race
    can't double-pay). txHash has a unique index — a given transaction can
    only ever pay one order.

[x] Background monitoring (was the one open gap, now fixed): patient no
    longer has to call POST /payment/verify for the order to settle.
    - StellarService.findPaymentForOrder(): lists recent payments to the
      order's provider wallet via Horizon, filters by asset+amount, returns
      a candidate tx hash (or null). Reuses the existing verifyPayment()
      for the authoritative check (memo/destination/asset/amount) once a
      candidate is found — no duplicated validation logic.
    - ServiceOrdersService.reconcilePendingOrder() / findPendingOrders():
      the shared "mark PAID" logic (DB update + notifications + activity
      log) was extracted into applyVerifiedPayment() so both the
      patient-triggered path and this background path use the identical,
      single code path for actually settling an order.
    - ServiceOrdersMonitorService (src/service-orders/service-orders-monitor.service.ts):
      @Cron every 5 minutes, scans all PENDING orders, tries to reconcile
      each. Per-order try/catch (one Horizon failure doesn't kill the
      sweep) and a re-entrancy guard (matches the pattern already used in
      WalletTrustlineService).
    - The manual POST /payment/verify endpoint is kept — still useful for
      instant feedback in the UI right after the patient submits, instead
      of waiting up to 5 minutes for the next sweep.

PART 9 — Service-to-Transaction Association             STATUS: DONE
======================================================================

[x] txHash, paidAt stored directly on the service_orders row (see Part 5
    schema). Open Question 3 is now answered by this implementation: NO
    retry/child table — one order supports exactly one successful payment,
    txHash is unique across all orders. A failed verify attempt leaves the
    order PENDING and doesn't consume/burn the order; the patient can
    resubmit a different tx hash. If product later wants a full audit trail
    of failed attempts (not just the one that succeeded), that needs a
    child payments table — deliberately not built (would be premature
    normalization for what was asked).

NEW — USDC Trustline Automation (not in original brief text, found +
fixed during review of the settlement work)          STATUS: DONE
======================================================================

[x] src/wallet-maintenance/wallet-trustline.service.ts — @Cron, every 5
    minutes. Sweeps all wallets with a stored encryptedSecret (i.e. every
    wallet this server is actually able to sign for):
    - account doesn't exist on-chain yet -> funds via Stellar testnet
      Friendbot, then establishes a USDC trustline
    - account exists but has no USDC trustline -> establishes one
    - already has a trustline -> skipped
    - wallets WITHOUT a stored secret (would only happen for a
      hypothetically non-custodial linked wallet) are skipped — the server
      has no way to sign a ChangeTrust for those, by design.
    - per-wallet try/catch so one Horizon failure doesn't kill the sweep;
      re-entrancy guard against overlapping ticks.
    - notifies the wallet's owner (in-app notification) once fixed.
